# Decisions and assumptions

1. **Demo first.** The first experience is a seeded workspace with no login or API key. Demo evidence and plan progress persist in browser local storage; resume files are parsed by the server and discarded in demo mode. Live provider and Supabase persistence activate when credentials are configured. This keeps local setup and exploration possible without third-party accounts.
2. **Readiness is deterministic.** The documented formula is implemented in a pure module with a fixed `asOf` date input. Its component inputs are visible. The UI demo currently presents representative seeded values.
3. **Evidence must be confirmed.** Parsed skills are proposed evidence; unconfirmed entries do not contribute to readiness. Corrections belong to the user and should be recorded in `user_corrections` by a production mutation flow.
4. **Job provider fallback.** JSearch is attempted first, then Adzuna. Interactive and scheduled collection both use the per-user monthly JSearch counter, cache role postings for seven days, and fall back to Adzuna when JSearch is unavailable or capped.
5. **Weekly refresh worker.** A bearer-protected endpoint uses the server-only Supabase service role to page through every active target role. Pages contain four roles to fit the Vercel Hobby function window; GitHub Actions continues until the endpoint reports no next page. Failures are isolated per role. The worker persists postings, canonical requirements, skill-gap rows, and readiness snapshots, then retargets only pending plan tasks to current high-priority gaps. Completed and in-progress tasks remain unchanged. It uses deterministic plan templates so scheduled work does not depend on Gemini availability or consume Gemini quota.
6. **Supabase auth.** Email OTP and Google OAuth use Supabase Auth; configure redirect URLs and Google credentials in Supabase. The local demo deliberately remains usable without auth.
7. **Resume extraction.** PDF text uses `pdf-parse`; DOCX text uses Mammoth. This release stores extracted text and defers richer section inference to the validated Gemini wrapper. Contact-data redaction is applied before prompts.
8. **No auto-apply.** Application rows record user-entered actions only. There is no LinkedIn integration or automated application submission.
9. **Market and demo data.** Demo postings are fictional examples. External provider coverage, salary availability, regional Gemini handling, and licensing depend on vendor terms and configuration.
10. **Deployment target.** The app is designed for Next.js on Vercel Hobby, but Hobby is non-commercial and scheduled execution can be constrained. Use an external scheduler if required by the workload or plan.
11. **Workspace persistence.** Signed-in edits use the user's Supabase session and RLS through `/api/workspace`; browser local storage remains the offline/demo fallback. Removed target roles are archived with `is_active` so linked plans, postings, and readiness history remain intact. Apply every migration in timestamp order before enabling account sync.
12. **Live readiness inputs.** Readiness is recomputed from stored postings, canonical requirements, confirmed skills, completed gap projects, scored interviews, application outcomes, and posting dates/location. Requirement buckets use observed posting share (50% must-have, 25% differentiator); low-count application outcomes do not affect the score.
13. **Verifier demo switch.** The sidebar demo switch loads deterministic seeded content in the browser and prevents workspace, resume, and interview demo actions from writing to the signed-in account. Exiting reloads the saved workspace. The scheduled worker exits cleanly in demo mode and never modifies private accounts.
14. **AI-assisted resume, job, and plan flows.** Resume files are parsed locally first; Gemini may normalize the structured fields only when live mode and a key are configured. Every model evidence excerpt is checked against the redacted source before use, and users can edit the structured result. Job requirements use one batched Gemini extraction per refresh with canonical taxonomy hints and exact posting excerpts; keyword matching supplies a labeled fallback. Learning plans are drafted from persisted role gaps, weekly hours, and completed deliverables; regeneration leaves completed and in-progress weeks unchanged. Every flow returns its source (`ai`, `cache`, `fallback`, or `demo`) so the interface can label it honestly. Service-role AI usage attribution is restricted to the scheduled worker by migration `202611210004_service_api_usage.sql`.
15. **Sign-in first.** The root and private workspace routes require a Supabase session. The demo has its own `/demo` route and local-only navigation. Google OAuth is hidden unless `NEXT_PUBLIC_GOOGLE_OAUTH_ENABLED=true`; this flag does not enable Google inside Supabase, so the provider still needs valid Google OAuth credentials and an allowed callback. Email magic links remain available independently.
